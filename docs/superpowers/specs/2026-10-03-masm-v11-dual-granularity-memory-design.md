# MASM v1.1 双粒度记忆设计

## 1. 目标与证据

v1.0 的官方多模态 Smoke（任务 `teval_2224183c43fd8f3e`）完成 13/13 个流程节点，
但四项能力得分均为 0。服务器只读统计显示：34 次 Add 均为 `COMMITTED`，222 条
`source_messages` 对应 34 条 `memories` 和 61 条 Embedding；部分记忆摘要超过一万字符。
代码确认每次 Add 最终只构造一条 `MemoryDraft`。这些事实证明写入链路和向量生成正常，
也提示记忆粒度可能影响召回；目前没有官方逐题 Search 候选和 Answer 证据，不能把粒度
问题宣布为零分的已证实根因。

v1.1 的目标是在不改变官方 Add/Search 契约的条件下，让一条 Add 中的独立消息可被单独
召回，并保留整块上下文供关系推理。首先通过可脱敏的检索诊断和合成任务验证假设；
只有本地证据支持改动后，才注册新的官网版本并使用 Smoke 名额。

## 2. 范围与不可变边界

- v1.0 标签 `submission-rc2`、线上版本 `v1.0` 和既有评测数据保持原样。
- v1.1 继续使用 `official-masm`、`gpt-4o-mini`、`text-embedding-v4`、1024 维。
- 公开路由、认证头、请求与响应 JSON 外形、`top_k <= 100` 不变。
- Search 只返回可追溯记忆证据，不生成答案或推断出的新事实。
- 所有索引、治理、检索与删除操作继续以 `user_id` 为隔离边界。
- 不从官方隐藏数据集推断答案，也不把官方评测请求正文写入日志或仓库。

## 3. 方案比较与选择

| 方案 | 收益 | 代价与风险 |
| --- | --- | --- |
| 仅调整重排权重 | 改动小 | 无法增加被单条长记忆掩盖的候选粒度 |
| LLM 抽取原子事实 | 粒度细 | 增加模型调用、幻觉与证据追溯风险 |
| 确定性消息级记忆 + 整块记忆 | 粒度可控、原文可追溯、无需增加 LLM 调用 | 记忆与向量数量增加，检索需处理父子重复 |

选择第三种。这里的“原子”指一条原始消息或其有序内容单元，并不声称每条消息
只包含一个语义事实；对过长单条消息的句子级拆分留给后续实验证明必要性后再做。

## 4. 写入数据流

一次 Add 形成一个 `MemoryBundle`，内容按以下顺序排列：

1. 一条整块上下文记忆 `context`，保留 v1.0 的摘要与治理入口。
2. 每条非空原始消息对应一条 `message` 记忆，顺序与 `messages[]` 一致。文本保持原文；
   图文内容保留同一消息内文本与图片的顺序及关联。消息角色、时间戳和位置只作为
   来源元数据，不被当作模型生成的事实。

`Memory` 增加 `granularity`（`context` / `message`，非空，默认 `context`）和
`source_position`（从 0 开始、仅消息记忆有值）。旧记录迁移后均视为 `context`。
同一用户、请求和消息位置最多有一条 `message` 记忆；同一用户和请求最多有一条
`context` 记忆，由数据库部分唯一索引和事务内校验保证。来源消息继续作为不可变
原始证据保存；新字段不改变原有外键和旧记录的可检索性。

消息级文本向量使用现有 Embedding Provider 的批量输入，按返回 index 恢复顺序。
图片仍调用现有感知和向量链路；把 `embed_images` 目前逐张调用感知模型得到的
描述/OCR 与向量作为同一次计算结果返回，按图片输入顺序对应到来源消息，避免为
消息记忆再调用一次 LLM。映射数量不一致时 Add 在 claim 前失败，不写入不完整记忆。
纯图片消息的 Search 证据
使用已生成的忠实视觉描述与 OCR 文本，不直接返回内部对象 URI。只有官方契约允许
且经输出大小验证后，才考虑在 `ContentPart[]` 中返回图片 Data URI；默认方案只返回
可读的描述文本。

整块记忆仍是治理智能体的目标，`ValidatedActions` 只作用于第一条 `context` 记忆。
消息级记忆不独立触发治理智能体，也不修改既有记忆正文。任何模型或向量失败遵循
现有失败/降级语义；不得出现“部分消息提交成功、部分缺失却返回 Add 成功”。

## 5. 事务、幂等与删除

- 对同一 `(user_id, request_id)`，全部来源消息、整块记忆、消息记忆、向量和资产
  在现有 `finalize_request` 事务内提交，账本最后进入 `COMMITTED`。
- 已提交请求直接回放，不调用 LLM 或 Embedding，也不追加第二批消息记忆。
- 请求失败、所有权接管和暂存对象发布沿用现有 fencing token 与运行级锁。
- `delete_evaluation_run.py` 按 `user_id + request_id` 清理整块与消息记忆、向量、
  来源和对象；必须验证跨用户、共享对象和重试场景。
- 部署迁移只新增列与索引，不重写旧数据；迁移前仍做数据库和对象卷一致备份。

## 6. 检索与返回

词法、文本向量、图片向量和元数据通道照常在同一用户范围召回。候选带上
`granularity`、`request_id` 与 `source_position` 的内部元数据。排序时对消息级证据
给予受控优先级，同一次 Add 的 `context` 候选最多保留一条，且同源 `message` 更相关时
排在其前。重复内容通过来源位置去重，避免父子记忆占满 Top K。关系扩展仍以整块
治理节点为锚点，必要时把相关消息级证据补入候选。

重排的硬上限 64 和最终 `top_k=100` 契约需要一并核对：不能因 64 候选池让
Search 在已有足量相关消息时系统性丢失证据。`ResponsePacker` 仍返回完整证据，
不会截断单条内容；长整块记忆不得因排在首位而排挤更短且相关的消息证据。
返回的 `id` 指向实际记忆行，`content` 必须与可追溯来源一致。

## 7. 脱敏诊断与实验

每次 Search 记录匿名请求标识、运行档位、总候选数、各通道候选数、父子去重后数量、
最终返回数、响应字节数、耗时和状态码。不得记录 `user_id` 明文、查询、选项、记忆
正文、图片、Prompt、Key 或 Provider 响应。诊断必须有容量上限和日志轮转。

本地合成集至少覆盖：

- 同一 Add 内多消息的直接召回与消息位置保真；
- 单消息多事实的边界，检验是否需要下一轮进一步拆分；
- 跨 session 关系问题与整块上下文保留；
- 图文相邻和纯图片消息的检索证据；
- 无证据问题的空结果或低相关结果，不捏造答案；
- 多用户隔离、重复 Add、并发 Add、重启持久性、运行级删除；
- 旧记录迁移前后召回一致性及 30 MiB 响应边界。

使用同一合成语料、问题、模型设置和随机种子比较 v1.0 与 v1.1，记录 Recall@10、
Recall@100、证据覆盖率、平均/P95 Add 与 Search 时延、Embedding 输入量、模型
调用次数和成本。按问题类型分开报告，不用四类平均值掩盖单类退化。
先验证官方 Smoke 中零分的可能原因：若本地 v1.1 的候选覆盖和答案证据并未改善，
暂停发布并继续诊断，而不是仅凭记忆条数增加就重跑官方 Smoke。

## 8. 成本与发布门槛

以已观察到的 34 次 Add、222 条消息为上界示例，整块加逐消息记忆最多形成
256 条记录，是旧版 34 条的约 7.5 倍；空消息与实际策略可能降低数量。向量条数
和费用不能按记录数直接等比推断，实施后需测量。新增流程不得增加 LLM 调用次数；
如现有感知结果无法安全复用，必须先报告实际调用与费用，再决定是否纳入 v1.1。

发布条件：合同、事务、幂等、删除、隔离和迁移测试通过；合成集相对 v1.0 的
检索证据覆盖率有实测提升；并发 16/16 的官方入口下保持稳定；成本与超时符合
服务器容量。随后创建新 Git 标签和镜像，在独立 Compose 项目与数据卷上部署
v1.1，并使用 `v11.agentmemorydev.icu` 作为独立 HTTPS 地址。两套 API 共用当前
Caddy 的 80/443 入口：新增第二个站点配置，把 v1.1 域名转发到专用 Docker 网络
上的 v1.1 API；原有 `agentmemorydev.icu` 站点及 v1.0 API 路由保持不变，不能再启动
一个占用 80/443 的 Caddy。部署前先配置新域名 DNS，并验证两套 Health。
通过官网 `Add Version` 将新地址绑定为 `v1.1`，先运行新的 Multimodal Smoke。
只有 Smoke 的能力结果与错误信息可接受时才考虑 Full。
