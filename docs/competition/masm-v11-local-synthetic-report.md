# MASM v1.1 本机合成对照记录

日期：2026-10-03。代码基线：v1.0 `af9173f`，v1.1 独立工作树。两者均用
`local-fake`、同一台机器和本地测试 PostgreSQL；本轮在审查修复后重跑，每个能力类别只有 1 个固定用例，
不是官方赛题，也没有调用付费模型。完整聚合 JSON 由
`scripts/evaluate_synthetic_recall.py` 可重复生成；请求正文、图片和 Key 不进入报告。
同一轮两版本共享标记，但重复运行会生成新的标记后缀；本轮 32 个测试运行已按清单清理。

Recall@K 只要求某个标记出现在前 K 条证据中；因此一条包含全部标记的长上下文也可得满分。
“原子证据覆盖@K”要求每个标记至少出现于一条**只包含该用例一个目标标记**的证据，
衡量能否定位独立事实来源，而非标准基准 Recall。纯图片与无证据用例没有文本标记，
分别按非空和空结果计分。Top 100 的 v1.1 返回 100 条独立消息证据，v1.0 只返回一条
包含所有标记的长上下文。因此前 10 条的标准 Recall 在这个构造题上从 1.00 降至 0.10，
而独立来源覆盖@100 从 0 升至 1.00；这是目标冲突，不应只展示其中一个指标。
单条消息多事实在两个版本中均未被拆成独立证据，是当前粒度策略的明确边界。

本次平均 Add 时延：v1.0 34.89 ms，v1.1 67.84 ms；平均 Search 时延：
v1.0 11.72 ms，v1.1 16.91 ms。只有一次顺序本机运行，这些时延仅提示开销，
不能代表正式模型、云服务器或并发 16/16 的表现。Embedding 输入量、LLM/图片感知调用数
及成本在这次 HTTP 黑盒对照中不可观测，报告标为 `unavailable`，没有估算。

结论：标准 Recall 在其余七类简单样本上**没有提升**，Top 100 构造题的 Recall@10 还出现
退化；消息级证据的独立定位能力在多消息用例中提升，但单条消息多事实仍无改善，
同时本机时延增加。`local-fake` 不启用正式 MASM 的查询分析与重排，因此这些数值不能
代表正式服务的排序表现。需要再用正式模型、小规模盲测、多随机种子和容量测试核实，
否则不得据此发布线上 v1.1 或消耗官方 Smoke。v1.0 线上服务和既有评测数据未改动。
