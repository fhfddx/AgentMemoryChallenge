## 14. 既有记录的写入延迟与重试诊断（2026-10-04）

本节只读复核现有 7 份 v1.1 脱敏运行报告及当前代码路径；没有新增 Provider 请求、
数据库写入或付费测试。计量脚本记录的是每版 Add/Search 的整体平均与 P95、每次
HTTP 尝试的汇总数量和逻辑模型调用数，**没有持久化单次请求或流水线各阶段的耗时、
失败尝试的状态码/异常类型及其对应阶段**。以下因此区分结构性解释与不能定位的
具体故障。

- 已验证的结构：正式 v1.1 Add 先串行执行感知 LLM、历史召回、时序 LLM、管理
  LLM，再生成写入向量和提交；有文本时历史召回还会产生一次 Embedding 请求。
  v1.0 不装配 Add 智能体流水线。主模板三轮每轮 6 次 Add，均记录 21 次逻辑
  LLM 调用，其中 18 次对应 Add 的三阶段，余下 3 次对应复杂 Search；同轮
  Embedding HTTP 次数由 v1.0 的 12 增至 v1.1 的 18。Memora 的 3 次 Add
  对应 9 次写入阶段调用，另有 2 次复杂 Search 调用，合计 11 次逻辑 LLM 调用；
  Embedding HTTP 由 6 增至 9。这些调用数与代码路径相符。
- 已验证的延迟现象：主模板三轮没有失败 HTTP 尝试，但 v1.1 Add 平均仍为
  4546.42–5308.41 ms，v1.0 为 141.29–151.04 ms。因此“仅由重试造成写入
  变慢”已被无失败尝试的样本排除；串行的额外 Provider 路径是确定存在的主要
  结构性差异。现有汇总数据不能量化三个 LLM 阶段、召回 Embedding、写入
  Embedding、数据库与本机开销各占多少毫秒，也不能断言哪一阶段最慢。
- 已验证的重试现象：替代模板三轮分别记录 22/22、24/22、23/22 次
  LLM HTTP/逻辑调用，后两轮比逻辑调用分别多 2、1 次 HTTP 尝试；Memora
  为 12/11，多 1 次。合计 4 次额外 HTTP 尝试、4 次失败 HTTP、4 次
  `usage` 缺失，逻辑调用失败数均为 0。Provider 代码最多尝试 2 次，
  HTTP 错误和输出解析/校验错误均可触发重试；这里的失败尝试已被后续尝试恢复。
  不能从汇总值判定是 429、5xx、超时或其他错误，亦不能判定失败发生于 Add
  还是 Search。重试可能增加耗时与实际费用，但现有证据不足以计算其贡献或计费。

诊断结论：当前较慢的 Add 不依赖于偶发重试，首先应作为三次串行 LLM 加额外
Embedding 的架构成本审阅；重试是另一个已观察到、但根因和成本归属尚不明确的
波动来源。若后续获准继续开发，宜先在**不记录正文、密钥或原始响应**的前提下
增加阶段级耗时及失败尝试的状态/异常类别计量，再用受限样本验证瓶颈与重试
分布；本节不据此直接改算法、关闭重试或宣布性能门槛通过。OpenAI 专属费用、
图片路径、并发容量与官方成绩仍待验证。

## 29. 自然语言时间风险与融合试验冻结（2026-10-05）

只读审查复核确认，第 28 节的“日期之外无其它数字”只能排除含数字的
混合日期，**不能证明自然语言时间语义唯一**。例如
“October fourth to 2026-10-03” 或
“Today is 2026-10-03. Meeting tomorrow.”
仍可能通过入口校验；融合模型若仅引用其中的 ISO 日期，其输出也可能
通过现有证据校验而跳过旧时序分析。这是仍未解决的正确性风险，
不是测试套件、Recall 命中或默认关闭状态可以替代证明的事项。

此前已依次尝试提示词约束、日期证据校验、紧凑数字预检和单一数字日期
入口，每轮都揭示新的边界。继续罗列时间词或扩大正则无法可靠覆盖
自然语言的多时间关系，故本轮**停止对此融合方案追加启发式补丁**。
实验开关保持默认关闭，不得据历史小样本启用、部署或申报时延收益；
后续若继续该方案，需要重新设计可验证的时间语义边界，并用独立标注
样本与旧路径逐条比较事件时间及失败回退，而不是只看检索命中率。
本节只更正文档判断，没有新增代码或 Provider 请求。
