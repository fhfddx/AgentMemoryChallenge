# 我们做了什么、优化了什么（外行版详解）

- 文档日期：2026-10-21
- 对应版本：`codex/masm-v11-evidence-graph` 分支，线上 `162f5bc`
- 这份文档回答两个问题：**① 这两周我们具体做了哪些事？② 每一项优化改了什么、为什么改、结果如何？**
- 写法约定：每一项优化都按"做了什么 → 为什么要做 → 怎么验证 → 结果"四段说，尽量不用术语；必须用术语时会用括号给出人话解释
- 如果只想看结论：跳到第三部分"优化怎么变成分数"

# 第一部分 我们做了什么（六件事）

## 1.1 第一件事：读懂比赛规则，并把它翻译成一个可计算的策略

比赛规则看起来很多，真正决定策略的只有四条：

| 规则 | 人话 | 我们据此做的判断 |
| --- | --- | --- |
| 只交 Add（写入）和 Search（检索）两个接口 | 我们只负责"记住"和"找出来"，答题是平台的事 | 不在生成答案上花任何力气 |
| 模型被钉死（向量模型、大模型都固定） | 不能靠换更强的模型取胜 | 只能靠工程与判据设计 |
| 每个赛道只能正式评测 2 次 | 不能反复试 | 必须先造本地工具，把不确定性消灭在本地 |
| 总分权重是 检索 3 : 拒答 9 : 跨会话 1 | **拒答最值钱，是检索的 3 倍** | 把主要精力放在"该拒答时拒答" |

我们还从 12 次官方结果里反推出总分公式并在后续反复验证：

```
总分 = (3 × 检索 + 9 × 拒答 + 1 × 跨会话) ÷ 13
```

有了这条公式，很多决策就不用猜了。例如"跨会话做到满分能加多少分"——答案是 7.69，而"拒答多对一道题"能加 7.69。于是我们知道：**先修检索、再修拒答，最后才碰跨会话**。

## 1.2 第二件事：搭起一条完整的记忆系统

从零到能用，系统由四层组成（这里只讲每层"做了什么"）：

| 层 | 我们做了什么 | 外行理解 |
| --- | --- | --- |
| 写入 | 用大模型把对话拆成结构化记忆：事实、实体、时间、治理决策；再用代码逐项校验 | 把一段对话"编目上架" |
| 存储 | 建 10 张表，存原文、派生记忆、实体、事件、关系、向量、冲突版本 | 建图书馆的书架与索引卡 |
| 检索 | 八步流水线：分析 → 三路召回 → 融合 → 相关性闸门 → 重排 → 选择 → 证据图 → 打包 | 读者提问后，馆员找书的过程 |
| 治理 | 用户隔离、取代/冲突/合并、删除、审计日志 | 借阅规则与档案管理 |

## 1.3 第三件事：把"判断"从大模型手里拿回来，交给确定性规则

这是整个项目最关键的一次思想转变。

**原来的做法**：让模型判断"这些证据够不够回答问题"。
**问题**：比赛规定只能用 `gpt-4o-mini`（一个偏小的模型），它在"证据够不够"这件事上系统性偏向"够了"——于是大量本该拒答的题被答了，本该答的题又偶发被拒。

**后来改成**：模型只负责"提出建议"（比如"我建议把这条旧记忆标记为已被取代"），**能否执行由代码判断**，判断标准写死在代码里（目标必须属于该用户、动作必须在白名单、不能形成循环替代等）。

> 一句话：**模型负责理解，代码负责守门。**

## 1.4 第四件事：造了一套"不花官方额度也能验证"的工具

官方额度只有 2 次，所以我们自己做了四件工具：

| 工具 | 干什么 | 相当于 |
| --- | --- | --- |
| **探针**（5 个） | 往系统里写几条假数据，问几个问题，检查返回对不对 | 实验室里的小白鼠实验 |
| **逐例对比**（26 个固定案例） | 每次改动后检查"新结果是否包含旧结果""有没有带出不该出现的片段" | 改完代码先做回归测试 |
| **五轮稳定性门槛** | 同一批案例连跑 5 轮，每轮都要达标 | 防止"刚好这一次碰对了" |
| **进程内诊断脚本** | 在不改接口的前提下，把系统内部判断读出来 | 给系统装一个"体检仪" |

其中探针是最有价值的一项。举个例子，为了治"该拒答就拒答"，我们造了一个探针：写 4 条记忆，问 6 个问题——2 个必须答出来、4 个必须返回空。**只要这个探针不过，就绝不去动官方评测。**

## 1.5 第五件事：跑了 12 次官方评测，每一次都先写好"看到什么结果就怎么做"

官方评测前，我们会先写一张判读表，例如：

> 若 `拒答 22.22` 且 `检索 100` → 说明判据正确，继续沿此方向；
> 若 `检索 < 100` → 说明判据误伤，立即回滚到上一个已验证版本。

跑完之后**照表执行**，不做事后解释、不"再试一次看看"。这就是为什么 12 次运行里有 3 次是明确的失败（23.08、7.69、30.77 反复），但我们从来没有因为一次失败而浪费第二次机会。

## 1.6 第六件事：把所有失败都写成文档

我们保留了每一次被否决的方案，以及否决它的那个数字。原因很简单：**失败的模式比成功的技巧更可复用**。这份文档的第五部分就是这份"失败清单"。

# 第二部分 优化清单

下面按"收益大小"和"性质"分四组。每项四段：做了什么 / 为什么 / 怎么验证 / 结果。

## A 组：收益最大的一个优化——"只做加法"

### A1 加法式选择（项目转折点）

**做了什么**：原来我们让新的"证据图"模块**取代**原有的选择器。改成：原选择器的结果**原样保留**，证据图只在它后面**追加**那些"能证明有关联"的证据。

**为什么要做**：第一版"取代"方案官方只有 23.08，其中"单点事实"从 100 掉到 50。原因是我们新模块要求"证据必须完整"，而真实问题经常只能证明一部分——本来答得出的题被它判成"证据不足"。

**怎么验证**：做了一个逐例对比工具，对 26 个固定案例逐一检查"新结果是否包含旧结果的每一条"。

**结果**：检索从 66.67 提升到 **100.00**（满分），总分从 23.08 提升到 **30.77**。

**为什么这是最安全的优化**：它可以被数学证明——只要新模块只做"追加"，它就永远不可能删掉原有证据，因此检索指标**不可能比不开启时更低**。这是整个项目唯一一次"稳赚不赔"的改动。

## B 组：拒答优化（六代演进，一次比一次更精准）

拒答占总分的 9/13，是投入最大、失败最多的一块。我们前后做了六代判据：

| 代 | 判据（人话） | 官方结果 | 为什么失败/成功 |
| --- | --- | --- | --- |
| 1 | 让模型判断"证据不足"就不给 | 23.08 | 模型判断不可靠，把能答的题也拒了 |
| 2 | 请一个"判官"模型专门判断够不够 | 30.77（不变） | 判官太宽松，一次都没拒 |
| 3 | 让判官"从证据里抄答案"，抄不出就拒 | 30.77（不变） | 误拒了需要两个属性的问题 |
| 4 | 问题里的人名在候选里找不到就拒 | 30.77（拒答 22.22，但单点事实 50） | 池里没有 ≠ 库里没有 |
| 5 | 改成查整个库 | 30.77（单点事实回到 100，但直接事实 0） | 名字缺失但答案就在记忆里 |
| **6** | **"关系人名字"全库缺失才拒** | **38.46**（检索 100 + 拒答 22.22） | **成功：既拒该拒的，又不误伤** |

### B1 关键发现：单位弹性

第 4、5 代表面上不同，但实测总分都是 30.77。把数字代进公式就明白了：

```
3×100 + 9×11.11 = 400        （检索满分、拒答只对 1 题）
3×66.67 + 9×22.22 = 400      （检索掉一档、拒答对 2 题）
```

**每多答对 1 道拒答题，就恰好丢掉 1 道直接事实题。** 原因是这类判据都会命中"用户自己的名字不在记忆里"——记忆是第一人称写的（"我喜欢蓝色"），而问题常用名字称呼用户（"Alice 喜欢什么"），名字当然找不到，可答案就在里面。

### B2 第六代的成功逻辑

只用一种很窄的情形来拒答：**"关系人 + 名字"**，例如 `my sister Maya`。

| 情况 | 是否拒答 | 原因 |
| --- | --- | --- |
| 问题说"我姐姐 Maya 做什么工作"，而 Maya 全库不存在 | **拒答** | 任何记忆都回答不了这个问题 |
| 问题说"Alice 喜欢什么颜色"（Alice 是用户） | 不拒答 | 用户自己不会以"我姐姐 Alice"的形式出现，所以不会误伤 |
| 问题说"我的护照什么时候到期"，记忆里没这项 | 不拒答 | 名字不存在，交给原有逻辑判断 |

**怎么验证**：先在我们自己的拒答探针上跑（6 个问题全部符合预期），再跑 26 例对比（确认没伤到正例），最后才上官方。

**结果**：官方 **38.46**，检索保持 100 分，拒答 22.22（9 题对 2 题）。

### B3 另外两代安全但没命中的判据（保留在代码里）

| 判据 | 逻辑 | 为什么保留 |
| --- | --- | --- |
| 槽位模板近失配 | 名字位置通配、其余词序完全对齐的另一主体记忆存在 → 拒答 | 官方没命中，但逻辑无害，可覆盖"口令/编号"类问题 |
| 相关性闸门 | 相关性太低直接清空候选 | 这是第一道防线，天然安全 |

## C 组：跨会话优化（四层修复）

跨会话题长这样：

> 记忆 A："我姐姐 Maya 在 Zephyr 公司做建筑师。"
> 记忆 B："Zephyr 公司的年会定在 12 月 14 日。"
> 问题："我姐姐公司的年会是什么时候？"（问题里没提 Zephyr）

原来我们得 0 分。排查发现是**四层缺陷叠在一起**，逐个修好：

| 层 | 缺陷（人话） | 修复 | 验证 |
| --- | --- | --- | --- |
| 1 | 关键词检索要求"所有词都命中"，第二条记忆一个都没全中，根本没进候选 | 给图路径加了一条"任一词命中即可"的补充召回（有上限、只用于桥接） | 候选数从 1 变成 2 |
| 2 | 增强层只在"证据完整"时追加，从没主动找第二条会话 | 新增"桥接追加"：只追加一条、必须与问题相关且与已选证据共享稀有词 | 诊断显示 `bridge_added=1` |
| 3 | 补充召回用了问题里的词，`sister's` 这种所有格让数据库查询报错，异常被吞 | 查询词只保留字母数字 | 本地实测从"0 条"变成"2 条" |
| 4 | 判断"候选是否相关"时口径错，把桥接候选的关键词当成了"不存在" | 桥接候选用自己的关键词比较 | 返回结果从 1 条变成 2 条、来自 2 个会话 |

**结果**：真实管线验证通过（两条记忆、两个会话、桥接成功），待官方评测确认。**只要跨会话拿到 20 分，总分就是 40.00。**

## D 组：工程可靠性优化（让系统"不骗人、不丢数据、可定位"）

| 优化 | 做了什么 | 为什么重要 |
| --- | --- | --- |
| 日志白名单 | 只允许 55 个固定字段进日志，并把 14 个图相关字段补齐 | 之前漏字段导致所有图遥测被静默丢弃，排查多花一轮 |
| 探针体系 | 5 个可复现的小测试 | 探针不能失败就不算测量（第一版桥接探针曾"假通过"） |
| 逐例对比 | 26 例，检查"不退化 + 不带脏片段" | 每次改动前的最基本保障 |
| 五轮门槛 | 连跑 5 轮，每轮 ≥24/26 通过 | 排除偶然性 |
| 进程内诊断 | 不改接口，读取系统内部判断 | 响应里没有诊断字段，只能从日志取 |
| 批量修复 | 向量化请求按 ≤10 条拆批 | 供应商限制，超限会让写入停滞 |
| 幂等与并发 | 请求登记 + 租约锁 + 部分唯一索引 | 网络重传不会重复写入，也不会重复扣费 |
| 清理与删除 | 删除按"用户 + 请求"精确级联，资产目录回收 | 探针可反复运行、不留垃圾数据 |
| 跨平台校验 | 摘要改用内容摘要 + 统一行尾 | Windows 与 Linux 行尾不同，导致校验反复失败 |
| 降级标记 | 模型异常时写"基线摘要"并标记 `degraded` | 少记但不能丢，且事后能区分 |

# 第三部分 优化怎么变成分数

把每次官方运行按时间排开，就能看到优化与分数的对应关系：

| 版本 | 做了什么优化 | 总分 | 检索 | 拒答 |
| --- | --- | --- | --- | --- |
| 起点 | 无（图关闭） | 23.08 | 66.67 | 11.11 |
| 第一版图 | 图取代原选择器 | 23.08 | 66.67 | 11.11 |
| 同源窗口 | 相邻消息补全 | **7.69** | 33.33 | 0 |
| **加法式** | **只做加法** | **30.77** | **100.00** | 11.11 |
| 证明式否决 | 图判定不足就压掉基线 | 23.08 | 66.67 | 11.11 |
| 提示词扩展 | 严格不足提示 | 30.77 | 100.00 | 11.11 |
| 池内缺名 | 名字在候选池缺失就拒 | 30.77 | 66.67 | 22.22 |
| 全库缺名 | 改成查全库 | 30.77 | 66.67 | 22.22 |
| 仅标识符 | 只认数字/词内大写的名字 | 30.77 | 100.00 | 11.11 |
| 同框架近失配 | 内容词重叠即拒 | 30.77 | 66.67 | 22.22 |
| 槽位模板 | 词序模板对齐 | 30.77 | 100.00 | 11.11 |
| **关系前缀** | **关系人名字全库缺失才拒** | **38.46** | **100.00** | **22.22** |
| 跨会话桥接 | 补召回 + 稀有连接追加 | 待官方 | — | — |

### 三个可直接读出来的结论

1. **检索优化最"干净"**：加法式一次把 66.67 抬到 100，之后再没掉过；
2. **拒答优化最"贵"**：六代判据里只有一代成功，前五代要么原地踏步、要么把检索分数换过去；
3. **跨会话优化最"便宜"但分值低**：满分也只有 7.69，但它决定 38.46 能不能变成 40.00。

# 第四部分 为什么这些优化是"安全"的（方法论）

这是我们认为比具体技巧更值得讲的部分。因为官方额度只有 2 次，**"安全"本身就是一种能力**。

| 原则 | 具体做法 | 解决的问题 |
| --- | --- | --- |
| 只做加法 | 新模块不允许删除旧结果 | 杜绝"修好一处、弄坏一处" |
| 逐例验证 | 26 例逐一检查包含关系 | 拒绝"平均分看起来变好了"这种结论 |
| 预注册判读 | 运行前写好"看到什么就做什么" | 防止事后自我解释 |
| 一票否决 | 出现回退立即回滚 | 不赌 |
| 探针必须可失败 | 探针要能真的判失败 | 防止"假通过"骗自己 |
| 诊断优先 | 关键判断都带固定"原因字段" | 一次运行定位，不靠猜 |
| 失败留档 | 每个被否决方案都记下数字 | 不重复踩同一个坑 |

下面这条最能说明问题：

> 我们的桥接探针第一版"通过"了。后来发现：它检查的是"返回项里是否包含两个标记"，而其中一个返回项恰好同时含两个标记，于是它通过了——**但桥接其实没生效**。改成统计"返回的条目来自几个会话"之后，问题才暴露出来，我们又多走了两轮才修好。

# 附录 术语速查（外行版）

| 术语 | 一句话 |
| --- | --- |
| Add / Search | 写入记忆 / 检索记忆，比赛只考这两个接口 |
| 证据（evidence） | 我们返回给平台的记忆原文，平台据此答题 |
| 拒答（abstention） | 记忆里没有答案时返回空列表，而不是编造 |
| 跨会话（multi-session） | 答案散在两次对话里，需要拼起来 |
| 检索（Retrieval） | 综合 direct 与 atomic 两个子指标的检索能力 |
| 加法式 | 新模块只追加证据、不删除旧结果的架构 |
| 探针（probe） | 自己写的小测试，用真实接口验证某项能力 |
| 门槛（gate） | 官方评测前必须通过的多轮稳定性检查 |
| 单位弹性 | 两个指标互相抵消：涨一分必掉一分 |
| 白名单（allowlist） | 只允许固定字段进入日志的安全机制 |
