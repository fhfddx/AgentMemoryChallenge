## 第 0 节 三分钟讲稿（可以直接照读）

> 现在的大模型有个毛病：**记不住你**。你上周说对花生过敏，这周它还是会给你推荐花生酱。
>
> 这个比赛就是比谁能给 AI 装上"可靠的长期记忆"。参赛队伍只需要交两个网络接口：一个叫 **Add**（把对话内容存进去），一个叫 **Search**（给一个问题，把当时相关的原文找出来）。**答题和打分不由我们做**，平台拿我们找出来的原文，用同一个回答模型答题、同一套评分器打分，保证所有队伍在同一把尺子下比较。
>
> 难点有三个：
> 第一，**找得准**——问题和原文措辞往往不一样，要能对上；
> 第二，**该拒答就拒答**——记忆里压根没有这个信息时，要老实说"没有"，不能胡编；
> 第三，**跨对话拼图**——答案可能散在两次对话里，要能拼起来。
>
> 我们做了三代方案。第一代想让新模块取代原有选择器，结果反而把分数拉低；第二代改成"**只做加法**"——原来选中的东西一律保留，新模块只补它漏掉的、而且能证明关联的证据。这一改让"检索"指标从 66.7 直接拿到满分 100。
>
> 最难的是拒答。我们试了五种判断方法，前四种都出现同一个现象：每多答对一道拒答题，就会恰好丢掉一道本来答得出的题，总分原地不动。最后我们发现关键区别在"**关系人 + 名字**"这种问法：如果问题是"我姐姐 Maya 做什么工作"，而整个记忆库里从来没有出现过 Maya，那这题谁也答不了，必须拒答；而用户自己的名字不会以"我姐姐 XX"的形式出现，所以不会误伤。就靠这一条，总分从 30.77 提到 **38.46**。
>
> 这个比赛每个赛道只允许正式评测两次，所以我们的做法是：先做小测试探针 → 再做逐例对比 → 再过五轮稳定性门槛 → 最后才花一次正式额度。

## 第 1 节 比赛要求

### 1.1 背景：AI 为什么会"失忆"

大语言模型本身**没有记忆**。它的一次回答，取决于这一次对话里喂给它的文字（上下文窗口）。超出窗口的内容就"忘了"。

三种常见补救，各有各的问题：

| 做法 | 做法说明 | 问题 |
| --- | --- | --- |
| 把全部历史塞进上下文 | 每次对话都带上所有历史 | 上下文有长度上限，越长越贵越慢，且模型会"中间忘" |
| 只摘要关键信息 | 让模型定期写摘要 | 摘要会丢细节、会引入错误，且无法引用原文 |
| **检索式记忆**（本项目方向） | 把历史拆成条目存库，提问时检索相关片段 | 检索不准就会答错；该拒答时不拒答就会胡编 |

比赛考察的正是第三条路：**如何把记忆"存好、找好、用得稳"**。

### 1.2 比赛要解决的具体问题

官方给出的能力模型分三大块：

| 能力块 | 编码 | 具体含义 | 举例 |
| --- | --- | --- | --- |
| 召回（RECALL） | A 显式事实 | 事实、属性、来源、实体信息 | "我的护照号码是多少" |
| | B 关系与多跳 | 跨片段证据、关系链 | "我姐姐的公司的年会在哪天" |
| | C 时间与事件序列 | 日期、间隔、顺序、轨迹 | "我上次换工作是几月" |
| 适应（ADAPT） | D 记忆治理 | 更新、冲突消解、删除与遗忘 | "我搬到了新地址"（旧的要失效） |
| | E 个性化与关怀 | 偏好、背景、健康与心理关怀 | "我不吃辣" |
| 执行（ACT） | G 规则与流程 | 领域推理、流程执行、格式约束 | "按报销流程还差哪一步" |
| | **H 认知安全与隐私** | **稳健拒答**、最小披露、证据边界 | "我有没有说过我养猫"（没说过 → 拒答） |

比赛的核心矛盾就在这里：**A 类要求"该答就答"，H 类要求"没有就说没有"**。两者用同一条记忆库、同一个模型，判据一旦偏一点，就会互相伤害。

### 1.3 参赛方要交什么：只交两个接口

| 接口 | 输入 | 输出 | 通俗说法 |
| --- | --- | --- | --- |
| **Add** | 一次对话或事件（谁说的、说了什么、什么时间） | 成功/失败 | "记下来" |
| **Search** | 一个问题（可能带选项） | **记忆原文列表**（每条含 id、原文、相关度分数） | "想起来，并把当时的原文递上去" |

两个接口都是同步的，平台在评测时会大量、并发地调用。

**为什么只交这两个？** 因为比赛要比较的是"记忆能力"，不是"写作能力"。如果允许参赛方直接生成答案，那比的就变成了谁的模型会说话。

### 1.4 平台做什么：统一答题与评分

```
参赛系统（我们）             平台（Agent Memory Leaderboard）
──────────────             ────────────────────────────────
Add  ← 记忆数据            准备好统一的数据集与问题
Search → 记忆原文   ──►     Answer：用同一回答模型，只依据我们返回的原文生成答案
                            Eval：用同一套评分器 + 审计证据判定对错
```

这条分工带来三个后果，必须理解：

1. **我们返回什么，直接决定平台能答什么**：返回少了，答案缺失；返回多了，可能引入错误信息；返回错了，答案必错。
2. **返回"空"是一种有效输出**：当记忆里确实没有相关信息时，返回空列表就是正确答案的一部分（这就是 abstention 的机制）。
3. **不允许我们自己"修答案"**：Search 的返回里只有证据原文，不能有生成内容。

### 1.5 三个绝对禁止

| 禁止 | 原因 | 违规后果 |
| --- | --- | --- |
| Search 里生成最终答案 | 把记忆评测变成写作评测 | 判定不合规，成绩作废 |
| 针对公开题目硬编码 | 公开题只用于预检，正式评测用私有数据 | 私有数据会立刻暴露，且属于作弊 |
| 跨样本共享状态 | 不同用户的数据必须隔离 | 属于数据污染 |

补充：比赛允许"同一用户跨次对话"的记忆关联，但**不允许把 A 用户的信息用于 B 用户**。我们的实现里，所有数据库查询在 SQL 层就强制带 `user_id` 过滤。

### 1.6 模型限制：为什么这条最影响策略

为了公平，平台规定了各部件能用的模型：

| 部件 | 通俗理解 | 规定 | 影响 |
| --- | --- | --- | --- |
| Embedding（向量化） | 把文字变成"语义坐标"，让机器能比较"意思像不像" | 必须 `text-embedding-v4` | 大家一样，无法靠更强的向量模型取胜 |
| LLM（大语言模型） | 负责读、判断、抽取、规划 | 必须 `gpt-4o-mini` | **一个偏小的模型，它的判断力上限就是整个方案的上限** |
| Reranker（重排） | 把候选按"更相关"重新排序 | **不作限制** | 唯一能换的部件 |

这条规则解释了我们后来遇到的很多"改代码也修不掉"的问题：当错误源头是"小模型判断力不够"时，无论怎么调提示词、怎么加后处理，都无法真正修正。

### 1.7 额度：只有两次正式评测

> 每个评测账号在每个赛道，**最多提交 2 次完整评测（Full）**；第 2 次必须在第 1 次完成满 **30 天**之后。

失败或取消的任务可以断点续跑，不计为新的一次。但总体而言：

- 不能"多跑几次看哪个好"；
- 每次正式运行前必须几乎确定；
- 一次错误决定可能消耗掉整个赛道的额度。

我们的整套工作方法（见第 3.7 节）就是为了解决这个约束。

### 1.8 指标与权重：为什么说 9 比 3 比 1

平台最终给出四个数字：

| 指标 | 含义 | 通俗说法 |
| --- | --- | --- |
| **direct**（直接事实） | 问题与答案在同一段记忆里，且表述直接 | "我驾照几号到期" |
| **atomic**（单点事实） | 需要从一条记忆里取出单一事实 | "我姐姐叫什么" |
| **multi-session**（跨会话） | 答案散在多次对话里，需要拼起来 | "我姐姐公司的年会在哪天" |
| **abstention**（拒答） | 记忆里没有该信息，正确做法是拒绝 | "我说过我养猫吗"（从未说过） |

我们把平台三次给出的分数代进去，反推出总分公式，并在后续运行中反复验证（三个点完全吻合）：

```
总分 = (3 × 检索 + 9 × 拒答 + 1 × 跨会话) ÷ 13
其中 检索 = (2 × atomic + direct) ÷ 3
```

举例（我们的真实成绩）：

| 检索 | 拒答 | 跨会话 | 总分 |
| --- | --- | --- | --- |
| 66.67 | 11.11 | 0 | (3×66.67 + 9×11.11 + 0)/13 = **23.08** |
| 100.00 | 11.11 | 0 | (300 + 100 + 0)/13 = **30.77** |
| 100.00 | 22.22 | 0 | (300 + 200 + 0)/13 = **38.46** |

**这张表说明了三件事**：

1. **拒答最值钱**：拒答每涨 11.11 分，总分涨 7.69；检索涨 33.33 分，总分才涨 7.69；
2. **跨会话最不值钱**：满分 100 只贡献 7.69；
3. **要到 40 分**：需要 `(300 + 9×拒答 + 跨会话)/13 ≥ 40`，即 `9×拒答 + 跨会话 ≥ 220`。若拒答 22.22（=200），则跨会话只需 ≥20 就够了。

### 1.9 一个被忽略的细节：拒答只有 9 道题

拒答指标只有 **9 道题**：

- 答对 1 道 = 11.11 分；
- 从 11.11 提到 22.22 不是"提升了一倍能力"，而是"**多对了一道题**"；
- 因此单次结果波动很大，任何一次"提升"都必须能用机制解释，否则可能只是运气。

这也是我们坚持"每个机制都要在本地探针上先复现、再上官方"的原因。

## 第 2 节 项目框架

### 2.1 用图书馆理解整个系统

| 图书馆里的事 | 系统里对应的事 | 技术名词 |
| --- | --- | --- |
| 读者把书交给图书馆 | 用户调用 Add 接口提交对话 | Add API |
| 管理员读书、判断主题、贴标签 | 写入流水线理解内容、抽事实、抽实体 | Perception / Curator |
| 给每本书写索书号 | 把文字变成"语义坐标"（一串数字） | Embedding |
| 摆放书架、维护索引卡 | 存进数据库并建检索索引 | PostgreSQL + pgvector |
| 在书与书之间做"参见"卡 | 记录记忆之间的来源关系 | Provenance / Relation |
| 读者来问：有没有讲某事的书 | 用户调用 Search 接口 | Search API |
| 馆员先在目录里找、再去书架找 | 多路召回：关键词 + 语义 + 元数据 | Multi-channel recall |
| 把一堆书按相关度排序 | 融合打分、重排 | Fusion / Reranker |
| 挑出真正能回答的那几页 | 选择器挑证据 | Selector |
| 只把书递过去，不替读者写论文 | 只返回原文，不生成答案 | 比赛硬规则 |

### 2.2 三个必须懂的基础概念

**（1）API 是什么**

API 就是"两个程序之间约定好的对话方式"。比如 Add 接口约定：你发给我一个 JSON（一种文本格式），里面写清楚"谁、什么时候、说了什么"，我就存下来，回你一个"成功"。

**（2）向量/语义坐标是什么**

计算机不认识"意思"，但可以把一句话变成一串数字（例如 1024 个小数），意思相近的句子，这串数字也相近。于是"找意思相近的内容"就变成了"算两串数字的距离"。这就是语义检索。

**（3）为什么既要用关键词又要用语义**

| 方式 | 擅长 | 不擅长 |
| --- | --- | --- |
| 关键词（全文检索） | 精确匹配：人名、编号、型号 | 换个说法就找不到 |
| 语义（向量） | 换说法也能找到、同义表达 | 对罕见专名不够敏感 |

所以我们**两路都跑**，再把结果融合。这是"召回"阶段的核心设计。

### 2.3 数据进来之后：写入流水线

一条对话进来，会经过三个"工种"，最终拆成两类记忆条目：

```
对话原文
  │
  ├─ 感知（Perception）：有哪些事实/事件/偏好？实体是什么（人、地、时间、金额）？
  ├─ 时间（Temporal）  ：把"上周二""明年三月"换算成确定时间，并记录先后顺序
  └─ 整理（Curator）   ：拆成条目，写摘要，抽关键词
        │
        ├─ context 条目：一次对话的整段摘要（用来"看懂当时在聊什么"）
        └─ message 条目：单条消息原文（用来"精确定位到那一句话"）
```

**为什么要两种粒度？** 因为两种问题需要两种颗粒度：

- "我们上次讨论的项目方向是什么"→ 需要整段上下文；
- "我具体说的是 11 月 10 日还是 11 月 11 日"→ 需要原文那一句。

**同时记录来源关系**：每条记忆都知道自己来自哪次请求、第几条消息、与哪条记忆同源。这些关系后来成了跨会话推理的"桥梁"。

> 一个真实踩过的坑：用户只发了两句话，系统实际会存成 **3 条记忆**（1 条上下文 + 2 条消息）。早期我们误以为"只查到 1 条就等于答不了两个问题"，正是这个结构造成的。

### 2.4 提问之后：检索流水线八步

```
问题
 ① 问题分析：抽要素、实体、时间、是否带选项
 ② 多路召回：关键词一批 + 语义一批 + 元数据一批
 ③ 融合去重：统一打分、合并重复条目、限制候选数量
 ④ 相关性闸门：明显不相关的剔除（这道门决定"要不要拒答"）
 ⑤ 重排：把最相关的排到前面（可用第三方重排模型）
 ⑥ 选择器：从候选里挑出真正支撑答案的若干条（核心判断）
 ⑦ 证据图（我们的增强层）：补上被漏掉但能证明关联的证据
 ⑧ 打包返回：受条数与字节上限约束，返回原文
```

每一步的"人话版"职责：

| 步骤 | 一句话职责 | 出错会怎样 |
| --- | --- | --- |
| ① 分析 | 弄明白用户在问什么 | 后面全跑偏 |
| ② 召回 | 把可能相关的都捞出来 | 捞不到 → 一定答不出 |
| ③ 融合 | 把多路结果合成一个候选池 | 池子太脏 → 后面被干扰 |
| ④ 闸门 | 把明显无关的清掉 | 太松 → 该拒答却作答；太紧 → 该答却拒答 |
| ⑤ 重排 | 让最相关的进前几名 | 排序差 → 选择器看不到对的证据 |
| ⑥ 选择 | 真正挑出能支撑答案的证据 | 挑错 → 答案错 |
| ⑦ 证据图 | 补关联证据（跨片段、跨会话） | 漏补 → 多跳题答不出 |
| ⑧ 打包 | 控制在条数与体积上限内 | 超限 → 请求失败 |

### 2.5 一次完整的端到端示例

**第一次对话（Add）**：用户说"我姐姐 Maya 在 Zephyr 公司做建筑师，她最近在准备年会。"

系统实际存成：

| 条目 | 粒度 | 原文（节选） |
| --- | --- | --- |
| ctx-1 | context | 用户介绍姐姐 Maya 在 Zephyr 公司任建筑师，正在准备年会 |
| msg-1 | message | 我姐姐 Maya 在 Zephyr 公司做建筑师，她最近在准备年会 |

**第二次对话（Add）**：用户说"Zephyr 公司的年会定在 12 月 14 日，我得买机票。"

系统存成：

| 条目 | 粒度 | 原文（节选） |
| --- | --- | --- |
| ctx-2 | context | 用户提到 Zephyr 公司年会定于 12 月 14 日，需要订机票 |
| msg-2 | message | Zephyr 公司的年会定在 12 月 14 日，我得买机票 |

**现在提问（Search）**："我姐姐公司的年会是什么时候？"

- ① 分析：问的是"时间"，关键实体是"姐姐""公司""年会"，但**问题里没提 Zephyr**；
- ② 召回：关键词路径只命中 msg-2（含"年会"），msg-1 因为不含"年会"被漏掉 → 候选池只有 1 条；
- ④ 闸门：这条通过（确实和年会相关）；
- ⑥ 选择器：选中 msg-2（含日期）→ 看起来可以回答；
- ⑦ **证据图（关键）**：系统发现 msg-2 与"另一个会话里提到 Zephyr 的记忆"共享一个**罕见词**（Zephyr），且那条记忆与问题共享"姐姐"这个要素 → 判定为可证明的关联 → **追加 msg-1**；
- ⑧ 返回：msg-2 + msg-1 两条，来自**两个不同会话** → 平台就能看出"哪家公司 + 哪一天"这条完整链路。

这个例子同时说明了三件事：为什么需要跨会话能力、为什么关键词检索会漏、以及"证据图"到底补了什么。

### 2.6 系统分三层

| 层 | 目录 | 通俗理解 |
| --- | --- | --- |
| 接口层 | `src/masm/api`、`src/masm/schemas` | 门卫：收请求、验身份、按格式回话 |
| 业务层 | `src/masm/services`、`src/masm/retrieval` | 车间：写入流水线、检索流水线、选择器、证据图 |
| 基础层 | `src/masm/storage`、`src/masm/providers` | 仓库与外部供应商：数据库、向量模型、大模型、重排模型 |

### 2.7 可观测性：看不见就修不动

每次搜索都会记录一份结构化诊断：候选多少条、选中多少条、是否回退、判定状态（充分/部分/不足）、是否拒答、耗时多少。

这些字段是**白名单**的：只有固定名字、固定取值的字段能进日志，绝不允许把用户原文或密钥写进去。

我们在这里吃过一次亏：白名单漏了几个字段，导致所有图相关遥测被静默丢弃，排查问题多花了一整轮。修好之后，任何"为什么没生效"都能从日志一眼看出。

## 第 3 节 项目优化

### 3.1 成绩曲线

| 阶段 | 总分 | 检索 | 拒答 | 跨会话 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 起点 | 23.08 | 66.67 | 11.11 | 0 | 第一版实现 |
| 加法式 | 30.77 | **100** | 11.11 | 0 | 关键架构改动 |
| **当前最优** | **38.46** | **100** | **22.22** | 0 | 拒答判据突破 |

### 3.2 第一次尝试：让新模块"取代"原选择器（失败）

**想法**：原选择器（内部代号 v7）判断力有限，那就再造一个更强的：

1. 让模型把问题拆成若干"需求"（比如"时间"和"地点"）；
2. 再去记忆里找能支撑每条需求的证据；
3. 最后把证据拼起来。

**结果**：官方 **23.08**，其中"单点事实"从 100 掉到 50。

**原因**：新流程只在"能证明证据完整"时才给结果，而真实问题经常只能证明一部分。于是本来答得出的题，被它判成"证据不足"而不给。

**教训**：新模块再聪明，**也不能拥有否决旧模块的权力**。

### 3.3 关键转折：只做加法，不做减法

改动只有一句话：

> 先按原选择器的结果**原样交付**，再把它漏掉的、且我们能证明关联的证据**追加**在后面。

这带来一个可以用数学证明的性质：

> 新模块永远不会删掉原选择器已选中的证据，因此检索指标**不可能低于**不开启新模块时的水平。

官方实测：检索 **66.67 → 100**，总分 **23.08 → 30.77**。这是整个项目唯一一次"稳定拿到正收益"的架构改动。

**怎么证明"不会变差"？** 我们做了一个对比工具，对 26 个固定案例逐例检查两件事：

1. 新结果是否**包含**旧结果的每一条（不允许漏）；
2. 是否带出了**不该出现的敏感片段**（不允许越界）。

任何改动只要这项检查不过，就不允许上官方评测。

### 3.4 最难的攻坚：该拒答时拒答，又不误伤

这是权重最高（9/13）的一块。我们试了五种判据，每一种都有真实数字：

| 尝试 | 判据（人话） | 官方/实测结果 | 问题 |
| --- | --- | --- | --- |
| 1 | 让模型判断"证据够不够"，不够就不给 | 拒答 22.22，但单点事实 100→50 | 模型判断不可靠 |
| 2 | 另请一个"判官"专门判断证据够不够 | 一次都没拒答 | 判官太宽松 |
| 3 | 让判官"从证据里抄答案"，抄不出就拒答 | 误拒了需要两个属性的问题 | 任务形式错配 |
| 4 | 问题里的人名在**候选池**里找不到就拒答 | 拒答 22.22，但直接事实全丢（0） | 池里没有 ≠ 库里没有 |
| 5 | 同上，但改成查**整个记忆库** | 单点事实修好，直接事实仍为 0 | 名字缺失但答案在 |

#### 关键发现：单位弹性

第 4、5 次失败暴露出一个非常干净的规律：

```
3×100 + 9×11.11 = 400        总分 30.77
3×66.67 + 9×22.22 = 400      总分 30.77
```

**每多答对 1 道拒答题，就恰好丢掉 1 道直接事实题，总分原地不动。**

原因：这类判据会命中"**用户自己的名字**不在记忆里"。因为记忆是第一人称写的（"我喜欢蓝色"），而问题常常用名字称呼用户（"Alice 喜欢什么颜色"）——名字当然找不到，可答案就在记忆里。

#### 突破口：关系人

只在"**关系人 + 名字**"这种形式下拒答，例如 `my sister Maya`：

- 用户自己**永远不会**以"my sister Alice"的形式出现 → 不会误伤直接事实；
- `Maya` 在整个库里从未出现 → 任何记忆都答不了"我姐姐 Maya 做什么" → 必须拒答。

官方实测：**总分 38.46**，检索保持 100、拒答 22.22。这是第一个同时满足两边的判据。

### 3.5 跨会话为什么一直是 0

跨会话的题长这样：

> A（第一次对话）："我姐姐 Maya 在 Zephyr 公司做建筑师。"
> B（第二次对话）："Zephyr 公司的年会定在 12 月 14 日。"
> 问题："我姐姐公司的年会是什么时候？"

问题里既没提公司名，也没提日期，必须把两条记忆连起来。我们原来得 0 分，排查后发现四层原因叠在一起：

| 层 | 原因 | 人话解释 |
| --- | --- | --- |
| 1 | 关键词检索是"全部词命中" | 问题里词多，第二条记忆一个都没全中，直接没进候选 |
| 2 | 增强层只在"证据完整"时追加 | 从没主动去找"第二条会话" |
| 3 | 补充检索的查询词含 `sister's` | 数据库查询语法报错，异常被吞掉，等于没查 |
| 4 | 判断"候选是否相关"时口径错 | 把桥接候选自己的关键信息当成"不存在"丢掉了 |

四层全部修好后，真实管线验证通过：返回结果从 1 条变成 2 条、两条来自不同会话、诊断显示"桥接追加了 1 条"。

#### 为什么这件事决定 40 分

```
总分 = (300 + 9×22.22 + 跨会话)/13 = (500 + 跨会话)/13
40.00 分 ⇔ 跨会话 ≥ 20
```

也就是说，**跨会话只要拿到一点分（大约一道题），总分就从 38.46 变成 40.00**。

### 3.6 试过但放弃的方向

| 方向 | 做法 | 为什么放弃 |
| --- | --- | --- |
| 同源窗口扩展 | 把相邻消息一起取回补全 | 官方实测总分 7.69，直接事实归零 |
| 提示词扩展 | 在原选择器提示词里加"严格判定不足" | 官方实测分数完全不变（小模型不响应这类指令） |
| 换更强重排模型 | 接入 Qwen3-Rerank（规则允许） | 技术可用，但实测多会话无增益，还让"本应拒答"的题多返回 1 条 → 收益/风险约 1:9 |
| 用模型判断替代规则 | 各种"判官" | 小模型系统性偏向"证据够了"，无法校准 |
| 放宽到"任意大写名缺失" | 最直觉的判据 | 见 3.4 的单位弹性，必然抵消 |

### 3.7 工作方法：因为只有两次额度

| 步骤 | 做法 | 目的 |
| --- | --- | --- |
| 1. 探针先行 | 为每个指标造一个小测试，跑真实接口 | 在本地复现问题，不花官方额度 |
| 2. 预注册判读 | 运行前先写出"看什么结果做什么决定" | 防止事后自我解释 |
| 3. 逐例对比 | 26 个固定案例逐例检查不退化 | 防止"这边涨那边跌" |
| 4. 五轮门槛 | 连续跑 5 轮，每轮 ≥24/26 通过、每例 ≥4/5、敏感片段为 0 | 排除偶然 |
| 5. 诊断优先 | 关键判断都带固定"原因字段" | 一次运行定位，而不是反复猜 |
| 6. 一票否决 | 出现回退立即回滚 | 不赌 |

**一个反例**：我们的跨会话探针第一版"通过"了，但实际上一个返回项里同时含两个标记，桥接根本没被验证。改正后才发现真问题，于是多走了一轮。所以有句话我们写进了文档：**一个不能失败的探针，不是探针。**

### 3.8 工程上踩过的坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 向量供应商批量上限 | 一次写入超过 10 段文本就报错，写入停滞 | 分批发送 |
| 日志白名单漏字段 | 关键遥测全部消失 | 补字段 + 加回归测试 |
| 行尾差异 | Windows 文件是 CRLF，摘要对不上 | 用内容摘要 + 统一行尾 |
| 文本工具破坏编码 | 中文注释变乱码、文件头多出隐藏字符 | 改用专用编辑工具 |
| 网络不可达 | 推送代码反复超时 | 走本机代理 |
| 长命令断线 | 输出被截半 | 单条命令限时、长任务后台跑再轮询 |
| 测试库未启动 | 全量测试挂死 | 先起临时数据库 |

### 3.9 如果只记三件事

1. **只做加法**：新模块不许否决旧模块，这是唯一稳定正收益的架构选择；
2. **单位弹性**：当两个指标互相抵消时，先算清楚抵消比例，再决定要不要做（这条公式替我们省掉了至少三次无效官方运行）；
3. **探针质量决定迭代速度**：不能失败的探针会骗人，害你多走两轮。

## 第 4 节 如何向别人讲解

### 4.1 一分钟版本

> 这个比赛是给 AI 装"可靠的长期记忆"。参赛队只交两个接口：一个存（Add），一个查（Search），答题和打分由平台统一做。我们做了三代方案，最有价值的一步是"只做加法"——保留原有结果，只补能证明关联的证据，让检索拿到满分。最难的是"该拒答时拒答"，我们试了五种方法，最后靠"关系人名字"这一条判据避免了误伤，把总分从 30.77 提到 38.46。

### 4.2 十分钟版本（分五段讲）

| 段落 | 时长 | 内容 | 关键句 |
| --- | --- | --- | --- |
| 开场 | 1 分钟 | 为什么需要长期记忆（花生酱例子） | "大模型没有记忆，这是产品级痛点" |
| 比什么 | 2 分钟 | 两接口 + 平台答题打分 + 三块能力 | "我们只负责记忆，不负责写作" |
| 怎么做 | 3 分钟 | 图书馆比喻 + 八步检索流水线 | "两路召回、一道闸门、一个选择器、一层证据图" |
| 难点与突破 | 3 分钟 | 只做加法；拒答五次尝试与关系人判据 | "每多对一道拒答题，就丢一道直接题" |
| 成绩与下一步 | 1 分钟 | 23.08 → 38.46；跨会话已修好，40 分差一步 | "跨会话只要拿到 20 分，总分就是 40" |

### 4.3 三个好用的比喻

| 要解释的概念 | 比喻 |
| --- | --- |
| 整体系统 | **图书馆**：编目上架、目录检索、只递书不写论文 |
| 两路召回 | **查字典**：一路按拼音（关键词），一路按意思（语义），两路都查更保险 |
| 加法式架构 | **助手不许改老师的卷子**：只能在后边补一页，不能划掉原来写的 |
| 拒答判据 | **点名**：如果问的是"我姐姐 Maya"，而全校没有叫 Maya 的人，那这题确实答不了；但别人叫你名字时，你当然要应 |

### 4.4 常见追问与回答

| 追问 | 回答 |
| --- | --- |
| 为什么不换更强的模型？ | 规则规定必须用小模型，正是为了公平；所以难点从"换模型"变成"在有限模型上做对工程" |
| 为什么不直接把所有历史塞进上下文？ | 有长度上限、成本高，而且越长越容易"中间遗忘"；检索式记忆才能扩展到几千条 |
| 为什么拒答这么难？ | 因为"记忆里没有"和"记忆里说法不同"在表面上看不出区别；偏严就会把能答的题也拒掉 |
| 你们最多的错误是什么？ | 早期是"用候选池判断有没有"，正确做法是"查整个库"；这个错误让直接事实一度归零 |
| 38.46 算好吗？ | 我们自己最好，但离满分很远；主要缺口是跨会话（0）和拒答只对 2/9 题 |
| 距离 40 分差多少？ | 差 1.54 分，等价于"跨会话答对一道题" |
| 为什么不多跑几次评测？ | 每个赛道只允许 2 次正式评测，第 2 次还要间隔 30 天 |
| 你们怎么保证改动不变差？ | 逐例对比工具 + 五轮门槛 + 预注册判读；出现回退立即回滚 |
| 跨会话为什么原来一直是 0？ | 四层原因叠加：关键词全命中、没有主动找第二条会话、查询语法报错被吞、相关性判断口径错 |
| 你们试过换重排模型吗？ | 试过（规则允许），技术上可用，但实测多会话无增益还会多带出无关证据，收益风险比约 1:9，所以没上 |
| 这个项目最难的地方是什么？ | 不是写代码，是"在只有两次评测机会的前提下做决策"——必须先把问题在本地复现出来 |
| 如果继续做，下一步是什么？ | 把跨会话从"已修复"变成"官方得分"，然后继续抬拒答（33.33 对应总分 46.15） |

### 4.5 讲的时候不要做的三件事

| 不要 | 原因 |
| --- | --- |
| 不要把"本地通过"说成"官方通过" | 两者差异很大，我们的探针就出现过假通过 |
| 不要只讲分数不讲机制 | 分数会被问"为什么"，机制才是可复用的部分 |
| 不要贬低比赛规则 | 模型限制和两次额度正是比赛设计的核心，难度也来自这里 |
