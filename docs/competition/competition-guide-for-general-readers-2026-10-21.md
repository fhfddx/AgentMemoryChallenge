# Agent Memory Challenge 参赛说明：要求、架构与优化（面向非技术读者）

- 文档日期：2026-10-21
- 对应代码：`codex/masm-v11-evidence-graph` 分支，当前版本 `162f5bc`
- 适合读者：产品、运营、投资、评审，或任何想弄明白"这个比赛在比什么、我们做了什么"的人
- 阅读顺序建议：先看第 1 节（比赛在比什么），再看第 2 节（我们搭了什么），最后看第 3 节（我们怎么把它做强的）

## 第 1 节 比赛要求

### 1.1 一句话说清楚这场比赛

**让 AI 拥有"长期记忆"，并且比谁的记忆更可靠。**

今天的 AI 助手有一个通病：聊完这一次，下一次它就不记得你了。你上周说过对花生过敏、上个月说过项目截止日是 11 月 10 日——下次对话它依然会重新问你，甚至给你推荐含花生的零食。

这场比赛要求参赛队伍做一个**记忆系统**：把用户说过的话、发生过的文件与事件存起来，并且在需要的时候**准确地找回来**。平台拿同一批数据、同一个回答模型、同一套评分器来考察所有队伍，避免"谁的模型强谁赢"这种不公平比较。

### 1.2 参赛方到底要交什么

只需要交**两个网络接口**（API）：

| 接口 | 作用 | 通俗解释 |
| --- | --- | --- |
| **Add**（写入） | 把一段对话、一个事件交给系统保存 | 相当于"记下来" |
| **Search**（检索） | 给一个问题，返回相关的记忆条目 | 相当于"想起来，并把当时看到的原文递上去" |

比赛方**只负责记忆**这两件事。真正的"回答问题"和"打分"由平台统一完成：平台拿你 Search 返回的记忆原文，交给同一个回答模型生成答案，再交给同一个评分器判断对错。

这条分工非常重要，因为它决定了一条硬规则：

> **Search 接口里绝对不能自己生成答案。** 你只能"递材料"，不能"替考生答题"。

### 1.3 比赛禁止的三件事

| 禁止 | 为什么 |
| --- | --- |
| 在 Search 里生成最终答案 | 否则比较的就不是记忆能力，而是写作能力 |
| 针对公开题目硬编码 | 公开题只是"预检"，正式评测用私有数据，硬编码会立刻现形 |
| 跨样本共享状态 | 每个用户的数据必须相互隔离，不能偷偷把 A 的答案用到 B 上 |

### 1.4 模型上的限制（这条规则最影响策略）

平台为了保证公平，规定了各部件能用的模型：

| 部件 | 规定 | 含义 |
| --- | --- | --- |
| 向量化模型（把文字变成"语义坐标"） | 必须用 `text-embedding-v4` | 所有人一样，不能靠更强的向量模型取胜 |
| 大语言模型（用来做判断、抽取、规划） | 必须用 `gpt-4o-mini` | 一个偏小的模型，**它的判断力上限就是我们的上限** |
| **重排模型（Reranker，用来重新排序候选）** | **不作限制** | 唯一可以自由更换的部件 |

这条规则后来成了我们的重要判断依据：当一个错误来自"小模型判断力不够"时，靠改代码是修不掉的，只能换思路。

### 1.5 评测额度：极其稀缺

> 每个评测账号在每个赛道，最多提交 **2 次**完整评测（Full）；第 2 次必须在第 1 次完成满 **30 天**之后。

这意味着**不能靠"多跑几次碰运气"**。我们的整个工作方法（见第 3 节）都是围绕这一条设计的：先在本地把候选方案验证到几乎确定，才允许动一次官方额度。

### 1.6 打分：四个指标，权重差别极大

平台把能力拆成三块，最后算一个总分：

| 能力 | 指标 | 考察什么 | 权重 |
| --- | --- | --- | --- |
| 检索（Retrieval） | **direct**（直接事实）+ **atomic**（单点事实） | 问题和答案在同一条记忆里，能不能找到 | 3/13 |
| 关系推理（Relational） | **multi-session**（跨会话推理） | 答案分散在多次对话里，能不能拼起来 | 1/13 |
| 证据治理（Evidence） | **abstention**（稳健拒答） | 记忆里**没有**这个信息时，能不能老实说"没有"而不是乱答 | **9/13** |

我们自己反推并用多次实测验证了总分公式：

```
总分 = (3 × 检索 + 9 × 拒答 + 1 × 跨会话) ÷ 13
```

**权重差异是关键洞察**：拒答占 9/13，几乎决定成败；跨会话只占 1/13。这意味着"费力提升跨会话"性价比很低，而"提升拒答"收益极高——但也最危险，因为判错了就会把本来答得出的问题也拒掉。

### 1.7 一个容易被忽略的细节：题量很小

拒答指标只有 **9 道题**，答对 1 道 = 11.11 分。也就是说"从 11.11 到 22.22"其实只是**多对了一道题**。这提醒我们：单次评测的波动很大，任何"看起来提升了 11 分"的结论都必须有机制解释，否则可能只是运气。

## 第 2 节 项目框架

### 2.1 整体像什么：一个图书馆

可以把我们的系统想象成一座图书馆：

| 图书馆 | 我们的系统 |
| --- | --- |
| 读者把书交进来 | **Add** 接口接收对话与事件 |
| 管理员编目、上架、做索引 | **写入流水线**：理解内容、拆条目、打标签、算语义坐标、建关联 |
| 书架与索引卡 | **数据库**（PostgreSQL + 向量检索扩展 pgvector） |
| 读者提问，馆员找书 | **Search** 接口：多路检索 → 过滤 → 排序 → 挑选 → 返回原文 |
| 只递书，不替读者写论文 | 只返回记忆原文，不生成答案（比赛硬要求） |

### 2.2 数据进来之后怎么存

一条对话进入系统后，会经过三个"工种"：

1. **感知（Perception）**：判断这段话里有哪些事实、事件、偏好，抽出关键实体（人、地点、时间、金额）。
2. **时间（Temporal）**：处理"上周""明天""三年前"这类相对时间，把它换算成确定的时间点，并记录先后顺序。
3. **整理（Curator）**：把内容拆成两类记忆条目：
   - **context（上下文条目）**：一次对话的整段摘要，用来"看懂当时在聊什么"；
   - **message（消息条目）**：单条消息，用来"精确定位到那一句话"。

两种粒度同时保存，是为了兼顾"整体理解"和"精确引用"。同时系统还会记录**来源关系**（哪次请求、第几条消息、哪两条记忆之间存在溯源关系），这些关系后来成了我们做跨会话推理的基础。

> 一个真实的坑：用户只发了两句话，系统实际会存成 3 条记忆（1 条上下文 + 2 条消息）。这一点在早期导致"检索到 1 条就等于答不了两个问题"的误判，是后来踩过的典型问题之一。

### 2.3 提问之后怎么找回来

Search 的过程像一条流水线，每一步都有明确的职责：

```
问题 → ① 问题分析（要素、实体、时间、选项）
     → ② 多路召回（关键词检索 + 语义检索 + 元数据检索，各取一批候选）
     → ③ 融合与去重（统一打分、合并重复）
     → ④ 相关性闸门（明显不相关的直接剔除，这一步决定"要不要拒答"）
     → ⑤ 重排（Reranker：把最相关的排到前面）
     → ⑥ 选择器（Selector：从候选里挑出真正支撑答案的若干条）
     → ⑦ 证据图（我们的增强层：补上被漏掉的关联证据）
     → ⑧ 打包返回（按字节上限与条数上限打包原始记忆）
```

其中：

- **②多路召回** 解决"记得住"：关键词负责精确匹配（人名、编号），语义负责"换个说法也能找到"；
- **④相关性闸门** 解决"不该答就别答"：相关性太低时返回空，这是 abstention 的第一道防线；
- **⑥选择器** 是判断核心：它看候选清单，输出"我选了哪几条、以及我是否确信"；
- **⑦证据图** 是我们加的增强层，详见第 3 节。

### 2.4 系统的三层代码结构

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 接口层 | `src/masm/api`、`src/masm/schemas` | HTTP 接口、请求/响应格式、鉴权 |
| 业务层 | `src/masm/services`、`src/masm/retrieval` | 写入流水线、检索流水线、选择器、证据图 |
| 基础层 | `src/masm/storage`、`src/masm/providers` | 数据库访问、模型供应商（向量、大模型、重排） |

### 2.5 可观测性（看得见才能改得动）

系统会为每次搜索记录一份**结构化诊断**，内容包括：候选数量、选中数量、选择器是否回退、判定状态（充分/部分/不足）、拒答与否、耗时等。

这些字段是**白名单**的：只有固定名称、固定枚举值的字段会被记录，绝不允许把用户原文或密钥写进日志。我们曾在这里踩过一次坑——白名单漏了几个字段，导致关键遥测被整体丢弃，问题排查因此多花了一轮。

## 第 3 节 项目优化

### 3.1 出发点和最终结果

| 阶段 | 总分 | 检索 | 拒答 | 跨会话 |
| --- | --- | --- | --- | --- |
| 起点（我们的第一版实现） | 23.08 | 66.67 | 11.11 | 0 |
| **最终（当前最优）** | **38.46** | **100.00** | **22.22** | 0 |

检索从 66.67 提升到满分 100，是这次最大的收获；拒答多对了 1 道题；跨会话仍未得分（原因见 3.5）。

### 3.2 第一次尝试：让"新的判断模块"取代原选择器——失败

我们最初的想法很自然：既然原来的选择器（内部叫 v7）判断力有限，那就用一个更强的流程替换它——先让模型把问题拆成若干"需求"，再去记忆里找能支撑每条需求的证据，最后拼成答案所需的证据集。

结果是 **23.08**：直接从 66.67 掉到 66.67（其中"单点事实"从 100 掉到 50）。原因很清楚：

> 新流程只有在"能证明证据完整"时才给结果，而真实问题经常只能证明一部分。于是本来答得出的题，被它判定成"证据不足"而不给了。

**教训**：新模块再聪明，也不能让它拥有"否决旧模块"的权力。

### 3.3 关键转折：只做加法，不做减法

我们把架构改成一句话：

> **先完全按原选择器的结果交付，再把它漏掉的、且我们能证明的证据追加在后面。**

这条改动带来一个可以用数学证明的性质：**新模块永远不会删掉原选择器已经选中的证据**，所以检索指标不可能低于不开启时的水平。

官方实测：检索从 66.67 提到 **100**，总分从 23.08 提到 **30.77**。这是整个项目唯一一次"稳稳拿到正收益"的改动。

为了证明"不会变差"，我们还专门做了一个对比工具（`--compare`）：对 26 个固定案例逐一检查"新结果是否包含旧结果"，并统计"是否带出了不该出现的敏感片段"。任何一次改动，只要这个检查不过，就不允许上官方评测。

### 3.4 第二次攻坚：怎么"该拒答时拒答"而不误伤

这是本项目最难的一块，也是权重最高（9/13）的一块。我们试了五种判据，每一种都有实测数字：

| 尝试 | 判据 | 结果 |
| --- | --- | --- |
| 1 | 模型判断"证据不足"就不给 | 拒答升到 22.22，但单点事实从 100 掉到 50 |
| 2 | 另请一个"判官"模型判断证据够不够 | 判官太宽松，一次都没拒答 |
| 3 | 让判官"从证据里抄答案"，抄不出就拒答 | 误拒了需要两个属性的问题 |
| 4 | 问题里的人名在候选池里找不到就拒答 | 拒答 22.22，但直接事实全丢 |
| 5 | 把"候选池"换成"整个记忆库" | 单点事实修好了，直接事实又全丢 |

第 4、5 次失败揭示了一个非常干净的规律，我们叫它**单位弹性**：

> 每答对 1 道拒答题，就恰好丢掉 1 道直接事实题，总分永远是 30.77。

原因是：那类判据会命中"**用户自己的名字**不在记忆里"这种情况。因为记忆是以第一人称写的（"我喜欢蓝色"），而问题常常用名字称呼用户（"Alice 喜欢什么颜色"）——名字当然找不到，但答案明明就在记忆里。

**突破口**：只在"**关系人 + 名字**"这种形式下拒答，例如 `my sister Maya`。理由很直接：

- 用户自己**永远不会**以"my sister Alice"的形式出现，所以不会误伤直接事实；
- 而 `Maya` 在整个记忆库里从未出现时，任何记忆都不可能回答"我姐姐 Maya 的工作"。

官方实测：**总分 38.46**，检索保持 100、拒答 22.22。这是第一个同时满足两边的判据。

### 3.5 第三次攻坚：跨会话推理为什么一直是 0

跨会话的题是这种形状：

> 记忆 A（第一次对话）："我姐姐 Maya 在 Zephyr 公司做建筑师。"
> 记忆 B（第二次对话）："Zephyr 公司的年会在 12 月 14 日。"
> 问题："我姐姐公司的年会是什么时候？"

问题里既没提公司名，也没提日期，必须靠"把两条记忆连起来"才能答。我们的系统原来是 0 分，排查后发现有四层原因叠在一起：

1. 基础检索用的是"关键词全命中"逻辑，问题里的词多，第二条记忆常常一条都没进候选；
2. 增强层只在"证据完整"时才追加，从没主动去找"第二条会话"；
3. 为桥接加的补充检索用了问题里的词，而其中 `sister's` 这种所有格会让数据库查询语法报错，报错被吞掉，等于没查；
4. 判断"这条候选与问题相关"时用错了口径，把桥接候选自己的关键信息当成"不存在"丢掉了。

四层全部修好后，真实管线验证通过：**返回结果从 1 条变成 2 条，两条记忆来自不同会话**，诊断字段显示"桥接追加了 1 条"。

跨会话只占总分 1/13，但它有一个非常现实的战略意义：

```
总分 = (3 × 100 + 9 × 22.22 + 跨会话) ÷ 13
40.00 分 ⇔ 跨会话 ≥ 20
```

也就是说，**跨会话只要拿到一点分（大约一道题），总分就从 38.46 变成 40.00**。这正是我们当前正在争取的目标。

### 3.6 试过但放弃的方向（同样有价值）

| 方向 | 做法 | 放弃原因 |
| --- | --- | --- |
| 同源窗口扩展 | 把相邻消息一起拿回来补全 | 官方实测总分 7.69，直接事实归零 |
| 提示词扩展 | 在原选择器的提示词里加"严格判定不足"的指引 | 官方实测分数完全不变（小模型不吃这套） |
| 换更强重排模型 | 接入 Qwen3-Rerank（比赛允许） | 技术上可用，但真实管线实测：多会话无增益，反而让"本应拒答"的题多返回 1 条 → 收益/风险约 1:9 |
| 让模型替代人工判据 | 各类"判官" | 小模型在这些场景上系统性地偏向"证据够了"，无法校准 |

每一项都在文档里留下失败记录与实测数字，避免后面的人重复试错。

### 3.7 我们建立的工作方法（这是最可复用的资产）

因为官方额度只有 2 次，我们把"省额度"变成了一套流程：

1. **探针先行**：为每个指标造一个"能跑真接口的小测试"。比如为了治拒答，我们造了一个探针：写入 4 条记忆，问 6 个问题——2 个必须答出、4 个必须拒答。探针不能失败就不算测量（我们的跨会话探针第一版"通过"其实是假通过，改正后才看到真问题）。
2. **预注册判读规则**：每次官方运行前，先写下"看到什么结果就做什么决定"，运行后照表执行，不做事后解释。
3. **逐例退化证明**：`--compare` 工具逐例检查"新结果是否包含旧结果"和"是否带出敏感片段"。
4. **多轮稳定性门槛**：连续跑 5 轮固定用例，每轮至少 24/26 通过、每个非豁免用例至少 4/5 通过、敏感片段为 0，才允许进入官方。
5. **诊断优先于猜测**：给关键判断加上固定枚举的"原因字段"（例如"为什么没桥接"），一次运行就能定位，而不是反复猜。
6. **一票否决**：任何一次官方运行出现回退，立刻回滚到上一个已验证版本，不"再试一次"。

### 3.8 工程上踩过的坑（挑几个有代表性的）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 向量供应商批量限制 | 一次写入超过 10 段文本就报错，写入停滞 | 拆批发送 |
| 日志白名单漏字段 | 关键遥测全部消失，问题无法定位 | 补白名单 + 加回归测试 |
| 行尾差异导致校验失败 | Windows 上文件是 CRLF，校验摘要对不上 | 用 git 对象摘要 + 统一行尾 |
| PowerShell 写文件破坏中文 | 注释变乱码、文件头多出隐藏字符 | 改用专用编辑工具，不用 shell 重写源码 |
| 网络不可达 | 推送代码反复超时 | 走本机代理 |
| 长命令断线 | 输出被截半 | 单条命令限时、长任务后台跑再轮询 |
| 测试库没起 | 全量测试挂死 | 先起临时数据库再跑 |

## 4. 一页总结

- **比赛**给了两个接口（写入、检索）、三块能力（检索、关系推理、证据治理）、四个指标，权重是 `3 : 9 : 1`，拒答几乎决定成败；模型被钉死、额度只有 2 次。
- **系统**像一座图书馆：写入时编目上架（理解、拆分、算语义坐标、记关联），检索时多路找书（关键词 + 语义 + 元数据）、过滤、排序、挑选，最后只递原文不写答案。
- **优化**的转折点是"只做加法不做减法"（新模块永不否决旧模块），让检索拿到满分；最难的是拒答，五次尝试后发现只有"关系人名字缺失"这一判据能既拒该拒的、又答该答的，把总分推到 38.46；跨会话的四层缺陷已全部修好，只等一次官方验证把总分推到 40。
- **方法**上最大的收获不是某个技巧，而是"探针 → 逐例证明 → 多轮门槛 → 官方运行"这套省额度流程，以及每次失败都留下可复现数字的习惯。
